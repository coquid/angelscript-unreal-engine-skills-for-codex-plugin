# 검증 기록

날짜: 2026-10-18. 포팅 버전: **0.1.0**. 업스트림: `a6aa73ada02a9fb1f5415bec491f9942c519b297`.

## 패키지와 도우미

로컬 환경: Windows, Python 3.14.2, PyYAML 6.0.3.

- `python scripts/validate_plugin.py`: 플러그인 식별 정보, 메타데이터, 스킬 참조, 라이선스, 기본 패키지 검사를 통과했습니다.
- `python -m unittest discover -s tests -v`: 이 Windows 호스트에서 **테스트 38개 중 36개 통과, 2개 건너뜀**.
  건너뛴 항목은 POSIX 모드 비트 보존과 이 Windows 프로세스에서 사용할 수 없는 심볼릭 링크 생성입니다.
- 설정 테스트는 쓰기 없는 미리보기, 명시적인 적용, 바이트·주석·BOM·CRLF 보존, 타임스탬프가 붙은 백업,
  멱등성, URL/이름 검증, 중복/프록시 충돌, 잘못된 TOML, 쓰기 실패, 동시 변경을 다룹니다.
- 문맥 테스트는 실제 프로젝트 식별 파일, 소스 트리, 중첩 디렉터리, 공백/Unicode, stdin JSON을 다룹니다.
- 패키징 테스트는 허용 목록, 스킬 리소스의 완전성, 재현 가능한 ZIP 바이트, 압축 해제 후 검증을 확인합니다.
- 압축을 푼 ZIP의 설정 도우미(미리보기/적용)와 문맥 도우미를 임시 디렉터리에서 추가로 실행했습니다.
- 스킬 3개 모두 skill-creator의 `quick_validate.py` 검사를 통과했습니다. UI YAML과 상대 참조도 확인했습니다.
- 독립적인 시나리오 검토는 사용자 지정 서버 이름/네이티브 카탈로그, 설정 범위, 오프라인 도구 작성,
  호스트 스킬과 UE 스킬의 구분, 결과가 불확실한 쓰기 작업을 다뤘습니다. 이제 복구 지침은 쓰기 작업을 다시 실행하기 전에 값을 다시 읽도록 요구합니다.
- 독립적인 코드/패키지 검토에서 남아 있는 차단 결함은 발견되지 않았습니다.

CI는 Windows/Linux와 Python 3.11/3.14에 대해 설정되어 있습니다. 실제 결과는
[GitHub Actions](https://github.com/Idris173/unreal-engine-skills-for-codex-plugin/actions/workflows/validate.yml)에서 확인할 수 있습니다.
이 문서는 설정된 CI 검증 범위를 원격 실행 성공과 동일시하지 않습니다.

## Codex 클라이언트 통합

클라이언트: Windows의 `codex-cli 0.163.0-alpha.10.2`. 자식 프로세스용 임시 `CODEX_HOME`과 일시적인
app-server 스레드를 사용했습니다. 사용자의 실제 Codex 설정과 플러그인 설치는 변경하지 않았습니다.

1. `codex plugin marketplace add`로 로컬 marketplace를 등록했습니다.
2. `unreal-engine-skills-for-codex@unreal-codex`를 설치했습니다. 클라이언트는 플러그인 버전이 0.1.0이고 설치 및 활성화되었다고 보고했습니다.
3. `skills/list`는 패키지 로드 실패 없이 플러그인 네임스페이스가 붙은 활성 스킬 3개 모두를 반환했습니다.
4. 설정 도우미가 임시 플러그인 설정을 유지하면서 테스트 엔드포인트를 추가했습니다.
5. Codex의 실제 MCP 클라이언트가 `connected`를 보고하고 `list_toolsets`, `describe_toolset`, `call_tool`을 발견했습니다.
6. app-server의 `mcpServer/tool/call`을 통해 툴셋/스키마를 탐색하고 현재 레벨 조회를 호출했습니다.
   실행 중인 테스트 프로젝트의 레벨을 성공적으로 반환했습니다.

이 결과는 설치, 런타임 스킬 발견, Codex 네이티브 MCP 호출을 검증합니다. 데스크톱 UI 검사나 모델의 자동 스킬 선택 성능 측정은 아닙니다.
임시 홈이 OS 임시 디렉터리 아래에 있어 PATH 별칭 경고가 발생했지만, 해당 도우미 별칭 없이도 설치·발견·호출은 성공했습니다.

## Unreal 통합과 에셋 저장 상태 보존

엔진: **5.8.3, CL 58210709**, Windows 설치형 빌드. 공식 ModelContextProtocol, ToolsetRegistry,
AllToolsets 바이너리가 있었습니다. 사용자가 지정한 테스트 프로젝트를 다음 인자로 실행했습니다.

```text
-EnablePlugins=ModelContextProtocol,AllToolsets
-ModelContextProtocolStartServer
-ModelContextProtocolPort=18765
```

격리된 테스트는 `http://127.0.0.1:18765/mcp`를 사용하고 MCP `2025-11-25`로 협상했습니다.
네이티브 HTTP 저장 상태 보존 테스트에서 전송 오류 없이 요청 26개가 완료되었습니다(HTTP 200 24개, 알림 HTTP 202 2개).
에디터 재시작 후 두 번째 세션이 수립되었습니다.

- 툴셋 55개를 발견하고 스키마를 읽었습니다. 등록 이름에는 모듈 이름으로 한정된 접두사가 포함되어 있었습니다.
- 실제 에디터 도구로 활성 레벨과 Actor를 성공적으로 조회했습니다.
- 고유한 `/Game/__CodexPluginSmoke/Session_.../` 디렉터리에 MaterialParameterCollection 하나를 만들었습니다.
- 명시적으로 지정한 해당 에셋만 저장하고, 파일이 존재하며(1,230바이트) `is_dirty`가 false인지 확인했습니다.
- 테스트 에디터를 정상 종료한 뒤 재시작하고 도구를 다시 발견하여 저장된 에셋을 로드했습니다.
- 재시작 전후 에셋의 SHA-256이 일치했습니다.
  `41f1e3d3e67c980847035e36698af1761df83c4b02360d556aca8dbb19f97719`.
- 네이티브 도구로 테스트 에셋만 삭제하고 새로 생성된 빈 디렉터리를 제거했습니다.
- `.uproject`와 `DefaultEngine.ini`의 해시는 유지되었으며, 기존의 관련 없는 에디터 프로세스는 작업 대상으로 삼지 않았습니다.
- 모든 전용 테스트 에디터 프로세스가 정상 종료되었고, Codex 클라이언트 확인 후 테스트 포트 18765가 해제되었습니다.

이 구성에서 엔진은 LiveCodingToolset을 제공하지 않았습니다. 이는 포팅된 스킬이 해당 도구의 존재를 필수로 가정하지 말고
사용 가능한 기능을 탐색해야 하는 이유를 뒷받침합니다. 엔진의 ProgrammaticToolset은 제한된 도구 실행 환경입니다.
이 포팅은 제한 없는 Python 실행을 가정하지 않습니다.

## 관측된 한계

- AllToolsets 때문에 테스트 프로젝트에 GameFeatureData Asset Manager 규칙이 없다는 GameFeatures 시작 오류가 발생했습니다.
  검증한 MCP/에셋 작업을 막지는 않았습니다. 이 오류를 숨기려고 프로젝트 설정을 변경하지 않았습니다.
  모든 영역이 필요하지 않은 프로젝트는 필요한 개별 툴셋 플러그인만 활성화할 수 있습니다.
- 이 엔진 설치에는 프록시가 없었으므로 프록시 설정/복구를 테스트하지 않았습니다.
- 실제 실행 검증은 Windows UE 5.8.3에서만 수행했습니다. Blueprint/Niagara/Control Rig/컴파일 영역을 폭넓게 검증했다고 주장하지 않습니다.
- 스크린샷 기반 시각적 인수 검증은 수행하지 않았습니다. 테스트 에셋은 렌더링되는 효과가 아닌 파라미터 컬렉션이었습니다.
- 선택적 문맥 도우미는 프로그램으로 테스트했으며, 사용자의 프로필에 자동 훅 활성화/신뢰 설정은 설치하지 않았습니다.
- 설정 도우미는 파일 하나를 검사하며 DNS 별칭을 해석하지 않고, 사용자 지정 ACL/xattr 대신 모드 비트를 보존합니다.
  적용 중에는 외부 쓰기 작업을 중단해야 합니다. 낙관적 재검사로는 잠금을 따르지 않는 외부 프로세스의 마지막 순간 쓰기를 완전히 방지할 수 없습니다.
- 공개 플러그인 디렉터리 제출은 이 릴리스의 범위에 포함되지 않습니다.

원시 RPC 추적, 로컬 설치 경로, 에디터 로그, 임시 프로필은 Git과 배포 패키지에서 제외합니다.
